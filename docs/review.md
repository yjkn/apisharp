# APISharp 项目 Review

## 1. 项目定位 Review

APISharp 的定位是 API 测试与管理平台，覆盖开发者导入 API、平台合规性检查、文档生成、测试人员编排用例、执行测试任务以及压力测试等流程。该定位具备较强的工程实践价值，能够连接开发、测试和接口治理流程。

建议在后续设计中明确平台边界：

- APISharp 应优先解决 API 元数据管理、测试用例管理、任务执行编排与结果追踪问题。
- Maven 插件应聚焦开发阶段的接口扫描、规范检查、文档生成和 API 注册，不应承担平台侧复杂业务逻辑。
- 执行器模块应与管理服务解耦，便于水平扩展和隔离高压测试带来的资源影响。

## 2. 技术架构 Review

规划技术栈为 Spring Boot、Maven、MySQL、MyBatis-Plus、Redis、JMeter、Elasticsearch。整体组合适合构建 Java 生态下的 API 测试平台。

### 优点

- Spring Boot + Maven 适合多模块后端工程组织。
- MyBatis-Plus 能提升基础数据访问层开发效率。
- Redis 可用于任务状态缓存、分布式锁、限流和执行进度同步。
- JMeter 成熟稳定，适合作为压力测试执行基础。
- Elasticsearch 适合存储与检索测试日志、执行记录和 API 文档索引。

### 风险与建议

- JMeter 执行任务可能消耗大量 CPU、内存和网络资源，建议执行器独立部署，并引入资源隔离与并发控制。
- API 注册与文档生成需要统一规范，建议尽早确定接口元数据模型。
- Elasticsearch 不建议用于强事务业务数据存储，核心业务数据仍应以 MySQL 为准。
- 测试任务执行应支持异步化，避免长时间占用管理服务请求线程。
- Maven 插件与服务端 API 之间需要版本兼容策略，避免插件升级导致注册协议不兼容。

## 3. 模块 Review

### apisharp-core

职责清晰，适合作为共享核心能力模块。建议包含：

- API 元数据模型。
- 合规性检查规则接口与默认规则实现。
- 文档生成抽象。
- 通用异常、响应模型、枚举与工具类。

### apisharp-maven-plugin

该模块是开发者入口，价值较高。建议重点关注：

- 支持在 Maven 生命周期中执行 API 扫描和校验。
- 支持本地生成文档与远程注册两种模式。
- 支持配置平台地址、项目标识、认证凭据和失败策略。
- 输出清晰的检查结果，便于开发者在 CI 中定位问题。

### apisharp-service

该模块是平台管理中心。建议包含：

- API 管理。
- 测试用例管理。
- 测试任务管理。
- 执行结果查询。
- 用户、项目与权限模型。
- 与执行器的任务分发接口。

### apisharp-actuator

该模块是测试执行器。建议包含：

- JMeter 测试计划生成。
- 接口测试执行。
- 压力测试执行。
- 执行结果采集与上报。
- 执行资源限制、超时控制和任务取消能力。

## 4. 数据模型 Review

建议优先设计以下核心实体：

- Project：项目空间。
- ApiDefinition：API 定义。
- ApiParameter：请求参数、路径参数、Header、Body 字段定义。
- ApiResponse：响应结构定义。
- ComplianceRule：合规性规则。
- TestCase：测试用例。
- TestStep：测试步骤。
- TestTask：测试任务。
- TestExecution：执行记录。
- TestReport：测试报告。

## 5. 关键流程 Review

### API 导入流程

1. 开发者在业务项目中引入 `apisharp-maven-plugin`。
2. 插件扫描项目接口定义。
3. 插件执行本地合规性检查。
4. 插件生成 API 文档。
5. 插件调用 APISharp 平台接口注册 API。
6. 平台保存 API 元数据并建立文档索引。

### 测试执行流程

1. 测试人员选择 API 并创建测试用例。
2. 测试人员将多个测试用例编排为测试任务。
3. 管理服务创建任务并分发给执行器。
4. 执行器生成 JMeter 测试计划并执行。
5. 执行器采集结果并回传管理服务。
6. 管理服务保存执行结果并生成报告。

## 6. 综合结论

项目方向明确，模块拆分合理。建议后续优先完成领域模型、模块骨架和 API 注册闭环，再逐步扩展测试编排、执行器调度、JMeter 压测和日志检索能力。
